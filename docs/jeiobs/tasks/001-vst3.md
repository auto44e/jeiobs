## Scope and cautions from upstream source

Host: plugins/obs-vst3. SDK finder: cmake/finders/FindSteinbergVST3.cmake.
`ENABLE_VST3` controls the host. The finder accepts `STEINBERG_VST3_PATH` pointing
to a directory containing `vst3sdk`. Inspect exact preset/dependency archives and
SDK revision, notices and license before fetching/integrating the SDK.

Upstream describes audio effects only, not instruments or MIDI; at most one main
input bus, one sidechain input bus and one main output bus. Linux implementation
is X11-focused. The module selection enables Windows/Linux x64/x86_64 and macOS.
Do not claim Windows ARM64, Wayland, Flatpak or arbitrary plugin compatibility.
A scanner helper exists; this is not evidence that DSP runs in an isolated worker.
This is source filtering, not the planned M2 master-bus processing stage.

## Runtime evidence (2026-11-15, branch `jeiobs/vst3-runtime-check`)

Status stays **In progress**. Reproduce with
`tools/jeiobs/vst3-check/run.sh BUILD_DIR DEPS_DIR` (Linux, `ENABLE_VST3=ON`).
Against the 672-step build on main `8c382452d` it printed 7 PASS, 0 FAIL. When I
replaced the ADelay class ID with a bogus one, the audio check failed and the
script exited 1, so that check does real work.

Test plugins: the SDK 3.8.0 samples `adelay` and `again-sample-accurate`, built
with VSTGUI and the hosting examples off. Together they expose 3 classes. The
broken bundles are: `invalid` (4 KiB of random bytes as the `.so`), `crash`
(`bad-crash.c`, raises SIGSEGV from a load-time constructor) and `hang`
(`bad-hang.c`, a load-time constructor that never returns).

| Case | Observed |
| --- | --- |
| No plugins | Scanner exits 1, prints `NO_VST3`, writes no list. |
| Good plugins | Scanner lists 3 classes. OBS logs them, exits with 0 leaks. |
| Invalid bundle | Skipped; the 3 good classes are still listed. |
| Crashing bundle | Scanner segfaults (exit 139) and writes **no list**. OBS survives ("Pipe closed before result") but offers **zero** VST3 plugins. |
| Hanging bundle | Scanner never exits; there is no scan timeout. OBS **hangs at shutdown** joining the scan thread; it exited about 1 s after I killed the scanner. |
| ADelay in a real mix | Tone onset moved by 1.078 s (expected 1.000 s; dry ≈0.58–0.61 s, wet ≈1.66–1.69 s, jitter ≈0.03 s). Peak 0.500 kept, no NaN/Inf. |
| AGain sample accurate | Output is silent (peak 0). **Cause: the SDK sample.** Its processor gain defaults to 0 (`SampleAccurate::Parameter` `initValue = 0.`), while its controller advertises 1.0; ADelay and "Advanced Tutorial" set their own processor defaults. In VST3 the processor owns state, so a host following the spec would also be silent. A smaller host gap: the host never syncs the controller from the processor (`getState` → `setComponentState`) after creating the plugin. |

The check treats the crash and hang rows as `INFO` lines that record current
behavior. The host-level crash check only asserts that OBS survives. These are
inherited upstream behaviors; follow-up work is in
[task 003](003-vst3-scanner-robustness.md). The extra 68–100 ms of delay is still
not attributed. The 10 ms block stage itself adds no delay (it is an exact FIFO
and stamps output 10 ms early). The likely cause is how libobs places late audio
(gaps under 70 ms are never corrected), but this is not proven. The method is
also noisy: dry and wet are separate OBS runs, each with its own media start-up
time. Measuring both in one run would settle it.

OBS runs get an unreachable PulseAudio/PipeWire server. Otherwise the default
Desktop Audio capture mixes whatever the machine is playing into the measured
output; a review run picked up a 0.91 peak from other audio.

The probes are throwaway OBS modules loaded only from the sandbox HOME.
`quit-probe` quits after load. `dsp-probe` plays a WAV through a media source,
optionally adds `vst3_filter` with a given class ID, and logs the tone onset and
peak of the final mix.

Still **not tested**: editor open/close, parameter changes, state save/reload,
bypass, plugin removal, sample-rate and channel changes, recording/stream
output, the real-time/thread review, macOS and Windows, and a Flatpak build.
